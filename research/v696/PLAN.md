# v696: cognitive search — the plan

Adrian (2026-09-27): *"Search should be cognitive, this is something we should
have already with the trie-based architecture."* And: *"plan first and then
execute broadly and systematically."* This file is the plan, written before any
code. It is the contract the work is held to.

## What is being built, in one paragraph

Programming (TypeScript) as a world whose checks are exact, used to **prove and
then generalise** search that goes through the architecture's own mechanisms —
recognition, means-ends with a goal stack, chunking, a learned proposer — and the
paper's mechanisms the repo has not used yet: two tries filtering one answer
set, a coarse filter at every node, backward error-correction, and the executive
as a learned state machine. Every mechanism goes into the executive or the
tries, **not into a code module**, and is then turned back on the v691 planner
and the v694 designer. Brute enumeration exists only as the last resort, and how
often it is reached is a number we report.

## What exists and is reused (surveyed 2026-09-27)

| Piece | Where | What it already does |
|---|---|---|
| Executive | `v687/executive.py` | Operators over working memory; goal stack; impasse → subgoal; **means-ends over `needs`/`gives` slots** (E5); **chunks** of subgoals (E6); utilities with learning off (`RATE=0`); every effect declared |
| Planner | `v691/acting.py` | The executive over world actions (STRIPS): needs = preconditions, gives = adds, deletes handled by `Situation`; problems with oracles (`problems.py`) |
| Learner | `v691/lessons.py` | A step that fails is compared with times it worked: what it requires is learned |
| Designer | `v693`, `v694` | Forms with holes, a check of the whole spec, Occam, a learned proposer (order only), remembered ways by similarity, carry-out → surprise → redesign |
| Trie | `v687/trie.py`, `v689/episodic.py` | Allocation-counting predicate trie; `identify` walks it down (recognition); growth = allocation |

The observation the plan rests on: **composing pure functions is delete-free
planning.** A value, once computed, stays. A library function `f: A → B` is an
action that needs a value of type A and gives one of type B. The executive's
means-ends is already type-directed in all but name.

## The phases

Each phase ends with a measurement on the scoreboard (Phase 0) against a baseline
taken **before** the phase, on a dev split that may be looked at, and a held
split run once for the record.

### Phase 0 — measure first: the scoreboard and the code world's checker

1. **`research/bench.py`: one command, one scoreboard, a history.** Runs every
   suite, prints one table, appends a row per suite to `bench/history.jsonl`
   (gitignored? no — small, committed) with the commit it ran on. Suites:
   - planning: v691 samplers (blocks, errands, delivery), new seeds, checked
     against breadth-first search for the shortest plan: solved, optimal,
     steps, search cost;
   - designer: v694 BANK/HELD/HELD2, v693 bank;
   - proposer: first-way-right and **designs imagined saved** (against the
     table order), not agreement with the designer;
   - common-sense actions: v695 PIQA dev (cached), held-out goals;
   - code: Phase 1's suites.
2. **The TypeScript checker** (`v696/tscheck.js` + `checker.py`): one
   persistent Node process running the compiler API in memory — type-check a
   candidate and run it on examples in milliseconds, not a `tsc` spawn per
   candidate. Both checks are exact.
3. **Code benchmarks.**
   - **Independent:** MultiPL-E HumanEval-TS (159) and MBPP-TS (~390):
     signature + examples in comments + hidden tests. Mostly beyond small
     composition — an honest ceiling, reported as is.
   - **Graded and unlimited:** tasks generated by composing the library at
     depth 1–4 from random seeds, with the composition kept as the known
     answer. Dev seeds and held seeds never overlap. This is where route
     breakdowns and learning curves are measured.
   - `regenerate` gets a `multipl-e` step.

### Phase 1 — programming as a world

- **Values are facts, types are slots**: `have s: string`. A task's inputs are
  the start; its output type (and examples) the goal.
- **The library is actions**, read from TypeScript's own `lib.d.ts` signatures
  through the compiler API (string, array, number, Math, a curated generic
  subset with instantiated type variables) — not written by hand.
- **Features of a specification** (as v693's `Spec.features`): input and output
  types, and what the examples show — same length, a sub-sequence, sorted, a
  count, a boolean over elements, a character-level change. These are the
  predicates recognition walks.
- A program is a plan; a plan is checked by the checker; nothing is trusted
  that did not type-check and pass every example.

### Phase 2 — the mechanisms, in the executive and the tries (general)

Each is a change to `v687/executive.py` or the trie, behind a switch, with the
existing suites run with it on and off. None names a type, a function or a
domain.

| # | Mechanism | Paper | What it is here |
|---|---|---|---|
| 2a | **Recognition before search**, unique-answer shortcut | §access/identification | A trie of solved problems keyed by their features, ordered by allocation; walking it down with a new problem's features returns candidates; one left → try it first, no search. The executive asks it before means-ends. |
| 2b | **Two tries, one answer set** | AND superposition | Forward: what can be derived from what is given. Backward: what could give what is wanted (regression). A candidate is where they meet. Bidirectional means-ends in the executive, for any planner. |
| 2c | **A coarse filter at every node** | Exp. 5, syllabic filter | A cheap check before an expensive one: types before running; in planning, relaxed reachability before expanding. The executive gets an operator-level `coarse` test run before `apply`. |
| 2d | **Backward error-correction** | reverse traversal | A failed candidate is walked back from its output on the examples to the first step whose value is already wrong; only that step is re-planned, not the whole program. Generalises v694's carry-out: a plan's failure is localised, not restarted. |
| 2e | **The executive as a learned EFSM** | executive memory | One learned proposer at the executive's level, (state features, operator) → utility, replacing the per-domain proposers of v693 and v694; utility learning (`RATE`) turned on where it is measured to help. |
| 2f | **Chunks become operators** | allocation = learning | A composition that solved a subgoal is kept as a new named operator (a helper function), offered to later problems like any other; unused ones are forgotten. The library grows by use. |

### Phase 3 — turned back on the planner and the designer

The same switches on v691's planning suites and v694's banks. The claim that
the search is cognitive and general is only made if it holds outside code.

### Phase 4 — on the page

*Write a function `f(xs: number[]): number` so that `f([1,2,3]) = 6`* — a
specification in the message, answered with the function, how it was found
(recognised / means-ends / chunk / last resort) and the checks it passed.

## The ladder: small functions are the first rung, not the goal

Adrian (2026-09-27): *"I'll want to extend this further, not just small
functions."* The rungs, each its own suite on the scoreboard as it is
reached:

1. **Expressions** — one function body composed from the library (Phase 1).
2. **Control** — conditionals, loops and folds as forms with holes (v693's
   forms), their bodies subgoals.
3. **Decomposition** — a function that needs helpers: the spec split into
   sub-specs, each a subgoal on the stack that becomes its own function,
   kept as an operator (2f) and reused. Hierarchical planning, the executive's
   goal stack doing what an HTN does.
4. **Editing existing code** — the world is a project, not an empty file:
   files, types and call graph read into the graph; actions are edits; the
   goal is a failing test turned green or a type error gone. Backward
   error-correction (2d) localises the fault.
5. **Projects** — several files, modules, an API to design to (v694's
   designer with interfaces as the thing-shaped holes), multi-step changes
   planned and carried out with surprises (a test that breaks elsewhere) as
   v691's impasses.

**What this forces now**, so the first rung does not have to be rewritten:

- A program is held as a **typed syntax tree with holes**, never as a string
  template: every rung's actions (compose, wrap in a form, extract a helper,
  edit) are operations on the tree, and the checker reads the tree printed.
- The world's state is a **type environment plus the tree**, not a set of
  values: the same state serves a function body and a project.
- The library is **read, not written**: from `lib.d.ts` for rung 1, and from
  the project's own declarations for rungs 4–5 — the same reader.
- Every result carries **how it was found** (the route), at every rung.

## What is measured, beyond "solved"

- **Route**: recognised, means-ends, from a chunk, repaired backward, last
  resort — per problem. The claim that search is cognitive stands or falls
  here: the last-resort share must be small and must fall with experience.
- **Cost**: candidates imagined, nodes expanded, checker calls, wall time.
- **Learning curve**: the same held tasks after 0, 100, 500 dev tasks seen.
- **Transfer**: planner and designer numbers with each mechanism on and off.

## Rules held to

- Baseline before each phase; dev may be looked at, held is run once per
  phase and never tuned on; hand-picked examples are never a claim.
- No LLM at runtime; models in `llm/` untouchable; anything gitignored
  rebuilt by `python -m regenerate`.
- Mechanisms general, or they do not go in. A change that only helps code is
  reported as that.
- Broader fixes over narrow ones. Commit only when asked.
